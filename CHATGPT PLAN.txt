# Part B — Let Amazon Q read your DB schema & sample rows (safe pattern)

Direct DB credentials in a general AI chat is risky. Instead, create a **read-only “metadata endpoint”** (Edge Function / tiny server) that returns sanitized JSON: table list, schema, and a few sample rows for requested table(s). Amazon Q reads that JSON and produces SQL, summaries, or validates code against schema.

## Why this pattern?

* Keeps DB credentials on the server (not in chat).
* Limits what Q can read (only what you expose).
* Easy for Q to reason about — it receives clean JSON, not raw DB.

## 1) Minimal secure endpoint: `/api/q/metadata`

Create an authenticated, read-only endpoint in your backend (or as a Supabase Edge Function) that accepts a small request and returns schema + sample rows.

### Example: Node / Edge Function pseudo-code (Express style)

(This is runnable or convert to Supabase Edge Function)

```js
// /api/q/metadata
// Input: { apiKey, tables: ["lots","operations"], sample_rows: 5 }
// Output: { tables: { lots: { columns: [...], sample: [...] }, operations: {...} } }

const express = require('express');
const app = express();
app.use(express.json());

app.post('/api/q/metadata', async (req,res)=>{
  const { apiKey, tables = [], sample_rows = 5 } = req.body;
  if (apiKey !== process.env.Q_META_KEY) return res.status(401).send({error:'unauthorized'});
  const result = {};
  for (const t of tables){
    // validate table names against an allowed-list
    if (!ALLOWED_TABLES.includes(t)) { result[t] = {error:'not allowed'}; continue; }
    const cols = await db.query(`SELECT column_name, data_type FROM information_schema.columns WHERE table_name=$1`, [t]);
    const sample = await db.query(`SELECT * FROM ${t} ORDER BY created_at DESC LIMIT $1`, [sample_rows]);
    result[t] = { columns: cols.rows, sample: sample.rows };
  }
  res.json({tables: result});
});
```

**Important:** keep `ALLOWED_TABLES` restricted (e.g., products, lots, operations, notes, note\_embeddings), and use a long random `Q_META_KEY`. Deploy this as a serverless Edge Function (Supabase Edge Functions, Vercel, or any server you control).

## 2) Generate detailed summary row for `summaries` table

You said you want a `summaries` table — create one that stores aggregated insights per day/branch.

**Prompt to generate a detailed summary for UI or to insert into DB:**

```
Using these operations (paste small list or example operations JSON), produce a detailed human-readable summary for Branch1 for 2025-09-17 that includes:
- total bags received,
- total parts produced,
- total cooked,
- total sold (by part & neck),
- leftovers (count & suggested price),
- anomalies (e.g., mismatch between produced and accounted-for).
Output JSON:
{"branch_id":"<id>","date":"2025-09-17","total_received_bags":int,"total_parts_produced":int,"total_cooked_parts":int,"total_sold_parts":int,"leftovers":[{"product":"", "parts":int, "suggested_price":int}], "anomalies":[ "..."]}
```

Store the output JSON into `summaries` table (you can create it like below):

```sql
CREATE TABLE summaries (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  branch_id uuid REFERENCES branches(id),
  date date,
  summary jsonb,
  created_at timestamptz DEFAULT now()
);
```

# Extra tips & guardrails

* **Always human-verify parsed JSON** before committing to DB — human-in-the-loop is essential for messy real-world notes.
* **Limit what you expose** in `/api/q/metadata` to a small, allow-listed set of tables and 5–10 sample rows — that prevents accidental data leaks.
* **Log Q interactions** for auditing (store prompts/responses in an `ai_audit_logs` table) so you can trace mistakes and improve prompts.
* **Rate-limit & batch** large tasks (parsing many notes, generating embeddings) to avoid hitting API quotas. If you want, I can write the batch scheduler code next.
